Design · chess-tools / chesspdf

Chesspdf Everywhere

把「棋书 PDF → 回放验证过的 PGN」做成一个宿主无关的 agent 能力:一份核心,任何 agent(Claude Code、Codex、Antigravity、pi……)都能跑,用户只需要一个 Gemini API key。

状态 草案 v1 · 2026-08-15  ·  依据 三本书实测(Imagination 756 题 / Woodpecker 1128 题 / Mastering 382 题)+ Agent Plugins 1.0 规范(2026-08-06)

1

目标与约束

  • 自主上书:给一本新棋书 PDF,agent 自己完成探查 → 选模板 → 调参 → 提取 → 验证 → 出 PGN,人工只处理残余队列。
  • 零 Claude 依赖的运行时:目标用户没有 Claude 订阅。chesspdf 引擎今天已只依赖 Gemini(识别 / re-OCR / 仲裁全走 GEMINI_API_KEY);本设计把「驱动循环的大脑」也开放为任意宿主 + 任意模型。
  • 一份源,多宿主:领域知识(playbook)、工具面、模板库只维护一份;每个宿主只有一层薄适配。
  • 验证优先:一切产出以「书中解答能在识别出的局面上合法回放」为准——这是领域内建的 oracle,也是自主化可行的根本原因。
2

分层架构

核心判断:宿主差异只存在于最外层。知识层用事实标准(SKILL.md / AGENTS.md),工具层只用最大公约数(CLI + JSON,不做 MCP),两层都与宿主无关。

L4 适配

宿主打包

Claude Code plugin · Agent Plugins 1.0 目录(Codex/ChatGPT/Cursor/Copilot/VS Code/Kiro)· Antigravity plugin · pi package。全部由同一份源生成,详见 §6。

L3 知识

Playbook(SKILL.md + AGENTS.md)

上书决策树、陷阱表(双写文本层 / span 空格丢失 / 误印锚点号…)、prompt 教训、验证纪律。SKILL.md 已是 Claude Code / Codex / pi / Antigravity 共同识别的事实标准。

L2 工具面

chesspdf CLI(JSON 输出)——唯一工具面

任何能执行 shell 的 agent 的最大公约数。工具用法由 SKILL.md 与 chesspdf --help 教给模型(pi 的 CLI+README 哲学)。不做 MCP:省掉一个协议层、一个常驻进程和每会话的工具 schema token 开销;若未来某宿主确有需要,MCP 只是对同一 CLI 的一层封装,随时可补。

L1 引擎

chesspdf Python 包

管线模板(born-digital 网格 / 扫描网格)、插槽契约、oracle(回放验证)、修复级联(fix_fens / fix_moves / fix_shifts)、bundle 状态机、review_app。只依赖 Gemini。

3

自主上书循环与升级阶梯

Agent 的工作被架构刻意降级:从「开放式编程」降到「对着 oracle 的参数搜索」。每一步都有客观反馈(锚点数 = 目录题数?回放率多少?),中档模型即可稳定完成大多数书。

probe → 判型(born-digital / 扫描) → 选模板 → 拟合 layout.json
      → ingest(锚点数 ≟ 目录题数,不等则回退调参)
      → recognize + solutions OCR → audit(回放率)
      → fix 级联 → 收敛 → assemble → 残余进人工队列
L0 · 模板 + 参数

大多数书

选管线模板,拟合 layout.json(锚点尺寸、分栏、单元格边距…)。出版社排版系统高度复用(Everyman、Quality Chess、Gambit…),几十个模板覆盖市场主体。

L1 · 插槽小函数

变体书

在签名固定的插槽内写 30–80 行函数:锚点探测器(页 → 格子)、棋盘解码器(格 → FEN)、解答切分器(页 → 题号+着法)。每个插槽有 oracle 可打分的合同测试。

L2 · 专家模式

新形态书

超出插槽范式时诚实上报,附探查报告。交给前沿 coding agent 或人,通过同一套接口(探查报告 + 插槽契约 + oracle)介入;产物固化为新模板,下个版本降为 L0。

4

工具面规格

所有工具 JSON-in / JSON-out、幂等、可续跑(仓库既有惯例)。图片走「写文件、返回路径」约定——宿主用自己的文件读取能力看图,对纯 CLI 工具面这是唯一自然、也是最可移植的多模态通道。放弃 MCP 的代价只有一个:宿主无法自动发现工具与参数 schema,可发现性全押在 SKILL.md 和 --help 的质量上——所以这两者按接口文档的标准维护,并纳入 CI。

工具作用关键输出
probe判型:文本层有无、字体清单、每页 drawings/图像统计、候选题目页{born_digital, fonts[], candidate_pages[]}
render渲染页面/单元格为 PNG,供 agent 看版式、调参{path, page, dpi}
layout set/get读写 layout.json 参数(模板选择 + 全部书调优数值)diff 后的完整 profile
run <stage>ingest / recognize / solutions / audit / fix-fens / fix-moves / verify / assemble阶段统计,如 {detected: 382, expected: 382}
report当前回放率、状态分布、失败题清单(audit_report 的浓缩){ok, illegal, var_only, …}
review queue导出残余题给人工(review_app 或静态清单)题号 + 图 + 候选 FEN

其中 probe / render / report 为本设计新增;其余是现有 CLI 的 JSON 化收口。

宿主适配矩阵

宿主SKILL.mdShell 执行AGENTS.md读图打包入口
Claude Code 原生Bash 原生Read Claude Code plugin(仅 skills)
Codex CLI 原生原生 原生多模态 Agent Plugins 1.0 目录(plugin.json + skills/,mcp.json 为可选项,直接省略)

pi 原生(与 CC/Codex 兼容)原生 原生模型多模态 同一 SKILL.md + CLI——与设计取向完全一致,零适配

结论:CLI-only 让适配矩阵塌缩成一个问题:「skill 文件放哪里」。所有终端型宿主都能执行 shell,工具面零适配;Agent Plugins 1.0 的 mcp.json 本就是可选字段,skills-only 的插件目录完全合规。目标宿主是终端型 agent;无本地 shell 的网页端宿主(如 ChatGPT 网页)不在支持范围,这是自觉的取舍而非遗漏。

仓库与打包布局

chesspdf/                    # L1 引擎 + L2 CLI(pip 包)
plugin/
├── skills/onboard-book/
│   └── SKILL.md             # L3 playbook,唯一事实源
├── AGENTS.md                # 项目级上下文(决策树摘要 + 纪律)
├── plugin.json              # Agent Plugins 1.0 manifest(skills-only)
└── adapters/
    ├── claude-code/         # 由 CI 从上述源生成(仅是目录结构差异)
    ├── antigravity/         #   └─ .agents/skills/ + AGENTS.md
    └── pi/                  #   └─ 原样复用,零转换
  • 单一事实源:SKILL.md 只写一份;各 adapter 由脚本生成(CLI-only 后只剩目录搬运),CI 校验漂移。
  • 知识/能力边界:skill 里不出现任何宿主特有指令;工具输出自描述,不假设驱动模型是谁。守住这条线,「换宿主」永远只是换壳。
  • Agent Plugins 1.0 的已知空白(无签名/密钥管理/沙箱)对本场景可接受:工具是本地 CLI,唯一密钥是用户自己的 GEMINI_API_KEY,由宿主环境变量传入。
7

Self-improvement 闭环

人工复核(review_app)产生的 verdicts 即新标签,回流三份真值集(756 / 1128 / 382,恰好覆盖三种书籍形态)。任何改进提案——prompt 调整、参数默认值、新模板——必须在真值集上回测过门槛(回放率不降、人工推翻率不升)才能合入。

纪律先于机制:项目自己的 prompt 教训表证明,没有评测集守门的「自我改进」会变糟(v2 自检 −7 分、v3 奇偶校验 −22 分)。飞轮的本质不是运行时变聪明,而是贵的智能的工作成果不断编译进便宜的运行时:模板库、playbook、插槽契约、评测集四样编译产物。

8

验证计划与开放问题

上书评测(每本新书记录)

  • 模板命中(L0 / L1 / L2)· 参数迭代轮数 · 人工干预次数(北极星指标)· 最终回放率 · 残余队列大小 · token 成本
  • 验收线:L0 书零干预跑通 ≥ 2 本,才投资 M3;否则把钱砸在卡住的那个插槽的工具化上。

开放问题

  • Antigravity headless / 脚本模式未见文档,发布前实测;闭源二进制带来 vendor 风险(退路:pi 或 ~300 行自研循环)。
  • L1 插槽内让中档模型写小函数的实际成功率——需要第四、第五本书的数据。
  • Agent Plugins 1.0 尚无 Claude Code / Antigravity 官方支持声明,adapter 生成层短期内不可省。
